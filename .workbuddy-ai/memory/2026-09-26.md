## 2026-09-26（18:30）🚨 训练 12 轮全跑完，但掩膜头是坏的 —— 已定位并修复

### 症状
fold 0 训完 12 epoch，loss 从 0.271 降到 0.039，**看起来完全正常**。
但用官方脚本在 fold 0 留出集上评分：**Mask mAP = 0.000000，num_predictions = 0**。

### 定位过程
1. 先怀疑推理代码：`predict_test.py --limit 5` → 0 实例。
2. 直接跑模型看原始输出（未经过项目代码）：
   - 训练图（见过）：2 个检测，max score 0.9986
   - **测试图（没见过）：5 个检测，max score 0.8161；另一张 max 0.9196**
   → 模型本身是好的，检测头正常。
3. 逐行插桩 `predict_image`，打印每一步：
   - `keep.sum() = 5`、boxes/masks 形状都对、NMS 保留 5 个
   - **但重建后的掩膜 `any per mask: [False, False, False, False, False]`**
   - RLE 编码全部抛 `mask is empty`
4. 打印原始掩膜数值：**`max=0.0096 mean=0.0000`** —— 掩膜头输出几乎全 0。

### 根因
`targets["masks"]` 形状错了。torchvision 要求 **`UInt8Tensor[N, H, W]`**
（已核对 site-packages 里 `mask_rcnn.py` 第 41 行文档），
而我的 Dataset 用 `np.stack(...)[:, None]` 产出的是 **`[N, 1, H, W]`**。

后果非常隐蔽：**检测头（box/cls）照常学得很好，只有掩膜头学废**，
而总 loss 里 `loss_mask` 接近 0 反而被当成"收敛得好"。
loss 曲线完全看不出问题——必须去看预测出的掩膜数值才能发现。

### 修复
1. `scripts/train_segmentation.py` 的 Dataset：去掉 `[:, None]`，掩膜改为 `[N, H, W]`
2. **加了 fail-fast 契约检查**：开训前取一个样本断言
   `masks.dim() == 3`、实例数三者一致、掩膜非全零，并打印形状
3. **训练日志现在逐项打印 loss**：
   `loss=0.9122 [box_reg=0.073 classifier=0.227 mask=0.516 objectness=0.084 rpn_box_reg=0.012]`
   —— 掩膜头塌缩会立刻在 `mask=` 上暴露
4. 新增 `tests/test_train_dataset.py`（7 个测试）守护掩膜目标契约

### 验证
修复后冒烟：`target contract OK: masks (2, 384, 683)`，
**`mask=0.516 → 0.406`（真实在下降，此前是塌缩到 ~0）**。86 个测试全绿。

### 现状
坏 checkpoint 改名 `fold0_brokenmask.pt` 留档，**正在用修复后的代码重训**
（fold 0，12 epoch，640px，`--no-resume`），日志 `outputs/logs/train_fold0.log`。

### 教训（值得记住）
**"训练跑完 + loss 下降"不等于"模型可用"。** 多任务 loss 里，

用户问「能否训练期间同时训 fold 1 做集成」。实测结论：**不行**。

| 指标 | 值 |
|---|---|
| 物理内存 | 25.7 GB (10 核) |
| **空闲 RAM** | **0.06 GB**（几乎为零） |

| Swapouts | 1,684,567（已在大量换页） |
| 磁盘 | 460 GB，已用 82%，剩 77 GB（充足） |

单个训练进程的内存构成估算：
数据集缓存 ~650 MB（560 图 × 640×360 缓存图 + 掩膜）
+ 模型与优化器状态 ~400 MB + 激活值 ~2–4 GB ≈ **3–5 GB**。

可回收内存只有 inactive 3.05 GB + free 0.06 GB ≈ **3.1 GB**。
再起一个进程需要 6–10 GB → **必然重度换页甚至 OOM**。

另外 MPS 是**单块共享 GPU**：两个进程会互相抢，各自速度大约减半，
总吞吐几乎不变 —— 并行没有任何收益，只有风险。

**之前 epoch 3 那次"被环境杀掉"很可能就是 OOM**，不是随机故障。

## 2026-09-26（21:20）🚨 第二个 bug：标签从 0 开始 → 只预测出一个类

### 背景
用修复掩膜形状后的代码重训 fold 0，跑到 epoch 7 时用 epoch-7 checkpoint 做了一次预评分：

| 类别 | AP_50_95 | AP50 | AP75 |
|---|---|---|---|
| 0 完整花穗 | 0.1331 | 0.3202 | 0.0477 |
| **1 不完整花穗** | **0.0000** | **0.0000** | **0.0000** |

**Mask mAP = 0.0666**。142 图 450 个预测，**全部是 category 0**，category 1 一个都没有。

### 根因
**torchvision 保留 label 0 作为背景，物体标签必须是 1..num_classes-1。**
而我的 Dataset 直接用了 0 基的提交类别 id（0/1）。

后果：完整花穗（id 0）被当成**背景**训练 → 模型学会不去检测它；
不完整花穗（id 1）被当成 class 0 → 模型检测到但标签错位。
结果就是"只预测一个类 + 类别全错位"，与观察完全一致。

更糟的是：**我写的 `tests/test_train_dataset.py::test_labels_are_in_submission_numbering`
反而断言了 labels ∈ {0,1}，把 bug 固化成"测试通过"**。这是我的错误——
我先把假设写进了测试，再用测试证明自己是对的。

### 修复
1. Dataset：`labels = category_id + 1`（预测端已经是 `category_id = label - 1`，正好配套）
2. **重写那个测试**：改为断言 labels ∈ {1,2} 且绝不出现 0，并新增
   `test_both_classes_are_present_across_the_dataset`
3. 开训前契约检查加断言：`min(labels) >= 1 and max(labels) < num_classes`
4. **新增 `scripts/verify_training_pipeline.py`**（这次缺失的关键工具）：
   过拟合 4 张探针图 150 iter → 在**同一批图**上推理 →
   断言两个类都能被检出、掩膜能编码成合法 RLE。

## 2026-09-26（22:19）澄清：Electron 崩溃不是我们的代码

用户发来 macOS 崩溃报告问「这是我们的报错吗」。

**结论：不是我们的代码，但根因相关。**

崩溃报告关键信息：
- 进程：`Electron`，`com.tencent.workbuddy.mac`（WorkBuddy 桌面应用本身）
- 崩溃点：`node::OOMErrorHandler` → `abort()`，SIGABRT
- 这是 **Node.js V8 堆内存耗尽**，不是 Python、不是 torch、不是我们的训练脚本

我们的训练是独立进程，**崩溃后依然存活**（21:38 崩溃，22:19 检查仍在
epoch 3/12 正常推进，loss_mask=0.195）。

根因同源：**系统级内存耗尽**（swap 已扩到 22.5 GB，用掉 21.9 GB，只剩 652 MB）。

这同时解释了之前的 SIGTERM 现象。

应对：
- 无法修复 WorkBuddy 应用本身（那是宿主程序，重启即可恢复）
