纪律（继承自团队上一届比赛的仓库）：**每次实验只改一个变量**，每条记录写清命令、
数字、以及它驱动的决定。没有记录 Mask mAP 的不算实验。

**配对规则（2026-09-28 加，代价是一次误判）：任何改动的结论必须来自 5 折配对比较。**
单折 140 图的 mAP 噪声在 ±0.7 pp 量级（E9 实测：fold4 上 +0.88 pp 的"明显胜利"，

只看一折的 Δ 会系统性地把噪声当成结论 —— 先在 5 折上算均值/标准差/胜负比，
再谈是否采纳；门槛仍是均值 ≥ 0.5 pp 且不能只有 1 折变好。

## E4 · 2026-09-28 · 训练轮数 12 → 24（**结果无效：续训实际零训练**）

- 改动   : `epochs` 12 → 24（fold 0，其余不变）
- 命令   : `python scripts/train_segmentation.py --folds 0 --light --short-side 640 --epochs 24`
  （夜间任务 `e4_fold0_epochs24`，23:19 启动，02:11 结束，10336s ≈ 2.9 h）
- 结果   : Mask mAP = **0.343386**，与 12 epoch **逐位相同**（590 预测也相同）
- 根因   : **续训没有真的训练。** `optimizer.load_state_dict()` 会连同 `lr` 一起恢复；
  epoch-12 的 cosine 调度恰好退火到 `lr = 0.0`，恢复后 scheduler 再 step 也始终把
  lr 写成 0（torch 2.14 实测：`_get_closed_form_lr()` 返回 0.0048，但
  `param_groups['lr']` 仍为 0.0）→ 12 个 epoch 全部空转。
  证据：`fold0.pt`（epoch=24）与 `solution.zip` 内 `model/fold0.pt`（epoch=12）
  **权重 SHA-256 完全相同**（`bd8188211826388a…`）。
  loss 0.2261 → 0.2247 的微小波动来自 batch 组成噪声，不是学习。
- 结论   : **E4 无结论，24 epoch 模型不存在。** 修掉 LR 恢复逻辑后才有意义。
  同时说明：**"loss 曲线正常 + 跑满轮数"又一次骗过了眼睛**，这次的检测手段是
  **对 checkpoint 权重取哈希**，而不是看日志。

## E7 · 2026-09-28 · 修复续训学习率（代码修复，非实验）

- 缺陷   : 见 E4 根因。`scripts/train_segmentation.py` 在恢复 optimizer 之前就建好了
  scheduler，导致恢复进来的 `lr = 0` 无人纠正。
- 修复   : 新增 `make_scheduler(torch, optimizer, epochs, start_epoch, base_lr)`
  —— 在恢复 optimizer 状态**之后**重建调度器，并从 `base_lr` 快进 `start_epoch` 步
  （cosine 的递推可望远镜式收敛到闭式解，所以快进后与"从未中断"的曲线逐点一致）。
  另加 fail-fast：若 `start_epoch < epochs` 且 lr ≤ 0 则直接报错退出，
  拒绝静默空转；每个 fold 启动时打印 `lr for epoch N = ...`。
- 验证   : `tests/test_train_resume_scheduler.py`（8 个测试）
  - 复现"跑满 cosine 后 lr 确实为 0"这一前提
  - 续训后 lr > 0（回归）
  - `start_epoch ∈ {0,1,5,12,23}` 时 lr 与闭式解在 1e-12 内一致，且后续 step 继续贴合
  - 全新训练仍从 `lr = 0.005` 起步
  - 用真实 checkpoint（epoch-24）复现：修复前 lr = 0.0，修复后 epoch 13 起为 0.002500
    （= 0.005·(1+cos(12π/24))/2），与未中断曲线一致
- 结论   : **保留。** 测试数 88 → **96**，全绿。

## E8 · 2026-09-28 · 复现抽查报 FAIL 是误报（代码修复，非实验）

- 现象   : 夜间任务 `repro_sample_check` 失败，`outputs/reports/repro_check.json` 里
  4 条 mismatch 的 expected/reproduced 实例数**相等**（8/8、10/10、9/9、3/3）。
- 诊断   : 逐实例比对后发现差异**只有 score 的第 6 位小数**（±1e-6）：
  MPS 上生成提交预测、CPU 上做复现，浮点路径不同。**实例数、category_id、RLE 分割
  完全一致**，4/8 图逐字节相同。
- 判定   : 官方复核标准是**复现后 Mask mAP 差 ≤ 0.005**（容差设计），不是字节一致；
  1e-6 的分数抖动远在容差内，且掩膜经 0.5 二值化、排序不变 → mAP 不受影响。
  此前的 fold0 单模型 CPU-vs-CPU 严格对比已证明代码路径本身正确。
- 修复   : `scripts/repro_check.py` 改为**分项比较**：`category_id` 与 RLE 要求严格相等，
  `score` 允许 ≤ `SCORE_TOLERANCE = 1e-5`；报告里新增 `score_tolerance` 与
  `max_score_delta`，把"容差有多大"变成可核对的证据，而不是把门槛调松了事。
- 结论   : **保留。** 提交包在实质上是可复现的。

### E8 续（提交 #3，多尺度）：RLE 也不能要求逐字节相等

多尺度提交复现时又撞上同一类问题：`IMG_337_aug1.jpg` 的某个实例**掩膜 RLE 字节不同**。
先做了判定性实验，确认不是包的问题：

| 比较 | 实例数/类别不一致 | 掩膜实质不同 | 最低掩膜 IoU | 最大 score 差 |
|---|---|---|---|---|
| 管线 CPU vs 提交（MPS） | 0 | 1 | 0.998495 | 2e-06 |
| **包内 CPU vs 管线 CPU** | **0** | **0** | **1.000000** | **0** |
| 包内 CPU vs 提交（MPS） | 0 | 1 | 0.998495 | 2e-06 |

包内推理与管线推理在同一设备上**逐字节相同** → 包是对的；差异只来自 MPS/CPU 浮点
（59 个实例里 1 个掩膜差了 0.15% 像素）。因此把 RLE 的"字节相等"也换成
**掩膜 IoU 容差 `MASK_IOU_TOLERANCE = 0.995`**，并输出 `min_mask_iou`。
这与官方口径一致：官方限定的是 **Mask mAP 绝对差 ≤ 0.005**，不是字节一致；
用 IoU 直接约束指标影响，比"看起来相等"更可辩护。
`tests/test_repro_check.py`（8 个测试）钉住这套判定语义（含"差一个像素应通过"
与"掩膜形状不同应失败"两侧边界）。

## E9 · 2026-09-28 · 推理分辨率 640 → 1024（**单折看着很香，5 折是无效结果**）

- 改动   : 推理 `short_side` 640 → 1024（权重不变、训练不变，唯一变量）
- 背景   : 发现推理分辨率被写死在 checkpoint 的 `short_side`（训练分辨率）里，

  2048×1152 的图缩到 640 只有 0.31×，掩膜边界精度损失直接体现在 AP75 上。
- 结果（单折，fold4）: 0.3602 → **0.3690（+0.88 pp）** —— 当时看起来是个明确的胜利
- 结果（补齐 5 折，同一留出折配对比较）:

  | fold | 0 | 1 | 2 | 3 | 4 | 均值 |
  |---|---|---|---|---|---|---|
  | @640 | 0.3434 | 0.3226 | 0.3500 | 0.3453 | 0.3602 | 0.3443 |
  | @1024 | 0.3503 | 0.3238 | 0.3507 | 0.3365 | 0.3690 | 0.3461 |

## E10 · 2026-09-28 · 多尺度融合 640 + 1024（**采纳，用于提交 #3**）

- 假设   : E9 显示两个尺度**单独看效果相当**，但它们的错误不一样（预测不同）；
  把两者融合起来，收益应该像多折集成那样来自多样性，而不是来自"更高分辨率"。
- 改动   : 每个 fold 在 640 与 1024 各推理一次，10 组检测并入同一个并集，
  再按类别 NMS(IoU 0.5) + 每图截断 100（与多折集成同一套融合规则）
- 结果   : 两条**互相独立**的测量给出同一个数字

  | fold | @640 | 多尺度（真实代码路径） | Δ |
  |---|---|---|---|
  | 0 | 0.3434 | 0.3490 | +0.56 |
  | 1 | 0.3226 | 0.3283 | +0.57 |
  | 2 | 0.3500 | 0.3572 | +0.72 |
  | 3 | 0.3453 | 0.3441 | -0.12 |
  | 4 | 0.3602 | 0.3691 | +0.89 |
  | **均值** | 0.3443 | 0.3495 | **+0.52 pp** |

  标准差 0.38 pp，标准误 ≈ 0.17 pp，5 折中 **4 折上涨** → 约 3 个标准误。
  另一条路径（离线合并两份已产出的 result.json）给出同样的 +0.52 pp，
  逐折数值也吻合（0.3493 / 0.3283 / 0.3564 / 0.3442 / 0.3692）。
- 结论   : **采纳，用于第 3 次提交。** 与 E9 的区别正是"融合"这个假设：
  不是单尺度更清晰，而是两个尺度的错误互补。
- 代码   : `scripts/predict_test.py` / `evaluate_local.py` / `solution/`（包内推理）
  统一支持 `--short_side 640,1024`；包内 `DEFAULT_INFER_SHORT_SIDES = (640, 1024)`
  与提交保持一致（否则赛后断网复现会算不出同样分数）。

### ⚠️ 这次实验过程中踩到的两个坑（都已修，留痕）

1. **实现与实验口径不一致。** 第一版多尺度支持里，收集检测的 4 行
   `*_all.append(...)` 缩进少了一层：单尺度下完全正常，多尺度下**只收集最后一个
   尺度的 score/label/mask**，某个尺度无检测时还会抛 `UnboundLocalError`。
   更糟的是部分折"成功退出"并给出看似正常的分数。
   已修，并新增 `tests/test_multiscale_predict_image.py`（3 个测试，用 stub 模型 +
   合成图，不需要真实权重）；**实测"故意回退缩进"会让该测试失败**，确认测试有效。
2. **官方评分脚本会被宿主机的删除保护拦下。** `official_evaluate.py` 开头调用
   `safe_unlink(score.json)` 清理上一轮成绩；若该文件**已存在**，删除动作触发
   `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` 并让评分进程 exit 1。
   现象具有误导性：同一批 5 折里，上一轮成功过的折全失败、上一轮失败过的折反而成功
   （因为它没有旧 `score.json` 可删）。
   **绕过办法：把 `--output_json` 指向一个尚不存在的路径**（`safe_unlink` 先查
   `exists()`，不存在就跳过，不产生任何删除）。用这条路径重新评分 5 折只需几秒，
   无需重新推理。
